# 04 流式语音：边想边说，切句、气口和延迟

> 初稿。标「待补」的地方需要我自己补录屏和听感对比。

目标：她一边生成文字一边开口，不用等整段写完；句子之间的停顿自然，不抢话、不吞句。

前提是第 03 篇的声音链路已经通了：中文 → 翻译成日语 → TTS → 播放。

## 先量，再决定改什么

我一开始以为瓶颈是「切块太粗」，量完才发现不是：

| 环节 | 实测 | 结论 |
|---|---|---|
| 翻译（带思维链） | 1.71 秒 | 关掉思考后 0.67 秒，译文一样 |
| 合成（40 步） | 1.87 秒 | 和句子长短几乎无关，是固定成本 |
| 合成（8 步） | 0.64 秒 | 步数是有效的旋钮，但音色会变，要靠耳朵定 |
| 她每句话的音频长度 | 2~3 秒 | |

她的句子本来就短，**瓶颈是每句的固定延迟**（翻译 + 合成 ≈ 3.8 秒），比音频本身还长，所以句子之间会露缝。

按收益排序做的：

1. 翻译关思考：每句省 1 秒，没有风险。
2. 并发预取：前一句在播的时候，下一句已经在合成。
3. 最后才做真流式通道。

> Irodori 是非流式引擎（Flow Matching），一块至少要 2 秒左右，**首个声音不可能低于约 2 秒**。想压到 1 秒以内只能换支持流式的引擎，我没换，因为要赌日语语感和音色还原度。

## 真流式通道：不换引擎也能做

AIRI 壳里本来就有一种 TTS 传输叫 `bidirectional-ws`：整轮回复开一条 WebSocket，**把 LLM 的原始 token 原样转发出去**，切句交给服务端。只有官方云服务用了它，但协议是现成的。

所以我自己写了一个本地服务（`tts/stream/`），实现这三个接口：

| 接口 | 用途 |
|---|---|
| `GET /api/v1/audio/speech/models` | 模型列表 |
| `GET /api/v1/audio/speech/voices` | 音色列表（壳要确认选中了音色才走流式） |
| `WS /api/v1/audio/speech/ws` | 收 `start` / `text` / `finish`，回 `sentence.start`、二进制音频帧、`sentence.end`，最后 `session.finished` |

壳那边加一个 provider：`transport: 'bidirectional-ws'`、`configuredBy: 'user'`、不需要凭据。官方那条是 `configuredBy: 'authentication'`，没登录根本选不到；provider 自己带上服务地址和令牌，否则没登录时令牌是空的，流式会**静默失败**，她一声不出。

收益全在「提前」：边收 token 边切子句，不等句号；切出来马上翻译；几句并行合成，壳按序号保序播放。

这套协议没有公开文档，是我照着壳的客户端代码一个字段一个字段对出来的。以真机联调为准。

### 做通道时踩的坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 连接建好了，一声不响就结束 | 判断「全部做完」时只数了队列长度。任务是先出队再合成的，第一句还在合成时队列已经空了，`session.finished` 提前发出、连接关闭 | 收尾要数「队列 + 正在做的」 |
| 每次重启 provider 都被打回默认 | 启动时角色卡会覆盖全局的语音设置（第 02 篇讲过） | 改角色卡，不是只改全局设置 |
| 日志里中文乱码 | `cmd /c … >> log` 下 Python 按系统码页写输出 | 启动脚本里 `set PYTHONIOENCODING=utf-8` |
| 流式服务没起，她连字都不出 | 壳等语音等到超时 | 语音服务挂了也要照样出字；启动脚本、关闭脚本都把这个端口加上 |

## 播放时序：抢话、吞句、抢句

这些是通道通了以后、真用起来才暴露的：

- **抢词**：新一轮回复开始时，壳会把还在播的语音**硬切**掉。改成 100ms 淡出，并在两轮之间加一道屏障。
- **抢句**：上一轮结束和下一轮开始之间没有气口，两句话贴在一起。每轮结束都写一道屏障，留 400ms 气口；**取消的时候也要补写**，不然旧段已经播完、旧轮还没关时会漏掉。
- **吞长句**：我做了流控（壳每播完一段回一个确认，服务端靠它判断播放有没有卡住），看门狗把长段当成卡死杀掉了。确认要校验，宽限时间要按实际进度重新算。
- **用久了变慢、丢句**：见第 03 篇，显存没还。另外渲染超时要放宽，慢句宁可晚出声也别丢。

## 切句节奏：听起来像一个人在说话

一开始切得很碎，半句半句地往外蹦，语调每段都像说完了。我最后定下的规则（都可以用环境变量调）：

- **只有第一块抢时间**：第一块按软规则早切，尽快出第一个声音；后面的块只在句末切，超过 64 个字才退到最近的逗号。
- **后面的块上限慢慢放大**：按上一块字数的 3.5 倍爬坡（最少 24 字），免得第二块太长，合成赶不上播放。
- **气口定长**：每段开头留 0.06 秒，结尾按标点定（句号、问号、感叹号 0.7 秒，逗号 0.3 秒，省略号 0.8 秒）。别让 TTS 自己决定停多久。
- **半句保持语调**：在逗号处切开的半句，译文用「、」收尾，TTS 念出来是「还没说完」的语调。
- **符号段并回上一句**：「实验做完了吗？……」这种，单独的「……」念不出来，并回上一句。

## 翻译这一步的坑（流式以后更明显）

逐段翻译后，翻译模型的毛病被放大了：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 说到一半停了 | 译文漏了一个分句或半句，没有报错 | 加完整性检查：译文的汉字 + 假名数低于原文的 0.9 倍，就按分句逐句重译 |
| 译文被截在引号那里 | 模型输出里有没转义的 `"`，解析时截断了 | 解析要求收尾引号后面紧跟 `,` 或 `}` |
| 一段空译文被悄悄丢掉 | 拼接时 `if o` 把空段滤掉了 | 有空段就整体算失败、重译 |
| 只有网址的那段，她念了一句自己编的台词 | 翻译模型不翻网址，干脆编一句「はい、指揮官……」 | 翻译前剥掉网址和路径，剩下没有能念的字就不出声、只显示字幕 |
| 心声被念出来了 | 流式下括号被切到不同的请求里（`（肩膀轻轻缩了缩，` / `）` / `让您戳。` 各是一个请求），成对括号过滤失效 | 改成跨请求的状态机，记住「现在在括号里」，加 30 秒超时兜底 |

## 情感（可选，我做得比较深）

后来我又让 TTS 按句子的情绪选不同的说法（亲密的句子用轻声、拒绝的句子别念得很开心）。做法是给每句先做一个情绪规划，再选对应的风格提示和引导强度。

这部分很容易陷进去。我的经验只有一条：**日志里字段全对，不等于听起来自然**。每一版都要导出音频自己听，留好冻结的输出和回滚开关，随时能退回上一版。

### 气口调整前后

[听一下对比（70 秒，MP4）](assets/04-pause-compare.mp4)：同一段话，前半是调整前（气口交给 TTS 自己定），后半是调整后（按上面的规则定长）。画面上是整段波形，句子之间的空白就是气口。

| | 调整前 | 调整后 |
|---|---|---|
| 这段话里三处停顿 | 1.39 / 0.40 / 0.31 秒 | 1.05 / 0.50 / 0.90 秒 |
| 8 段测试文本的停顿（共 15–16 处） | 平均 1.15 秒，最短 0.30，最长 1.93 | 平均 0.79 秒，最短 0.50，最长 1.05 |
| 首音延迟（平均） | 5.3 秒 | 5.2 秒 |

调整前最难受的是忽长忽短：有的地方停得像换了话题，有的地方两句贴在一起。调整后停顿只看标点，听起来就是一个人在连着说。首音没变慢，说明多出来的规则没拖慢第一句。

（录音开头等首音的那几秒我裁掉了，两段响度也拉到同一水平。同一段文本每次渲染，时序会有 ±1 秒的抖动。）
