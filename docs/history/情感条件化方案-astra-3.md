# 情感条件化方案 astra-3：流式与整段共用规划，按模型真实边界渲染

日期：2026-09-29。依据：`_tmp/task_astra3_longform.md`、中断会话实录、本机源码及 CPU 探查。

## 0. 裁决与范围

**推荐：保留现有生产入口，让流式和整段入口调用同一套带状态的情感规划器；整段输入允许后端按模型预算分块推理。先修条件选择和输入完整性，不直接把模型长度放大到 800 字。**

用户要求的是情感迭代适配 V2，流式、整段都能生产使用。“长段才听得出优劣”是听测材料要求，不等于所有长文本必须一次模型推理。本方案不为评测另造生产协议。

本轮只写此方案；没有修改生产代码、配置或模型，没有重启、GPU 合成、训练、部署或 push。下文标注区分：**实测**、**源码结论**、**待实施建议**、**未验证**。此前用户已确认的 300/500/800 字 token 统计及 CPU_boundary_checks 9/9 直接引用，未重跑。

## 1. 上限：200 字符、256 token、30 秒是三回事

### 1.1 真实底模与实际配置

**本轮实测：**实际底模为 `D:/AI/Wife/tts/irodori/checkpoints/model.safetensors`，文件大小 **3,064,295,596 B**；读取其 8 字节长度字段及 **86,048 B** 的 safetensors JSON 头，未载入张量。

`irodori_serve.py:21` 的 `CKPT` 指向这个位置，`_run_infer()` 显式传 `--checkpoint`。LoRA metadata 中的 `D:/AI/Irodori-TTS/...` 是旧路径记录，不能拿它作为当前服务加载位置。

| 项目 | 本机值 | 含义 |
|---|---:|---|
| checkpoint `config_json.max_text_len` | **256** | 文本 token 数上限，包含 BOS |
| `text_add_bos` | true | 留给正文的是 **255 token** |
| `max_caption_len` / `caption_add_bos` | **512 / true** | 条件提示词独立预算，包含 BOS |
| tokenizer | `sbintuitions/modernbert-ja-310m` | 优先加载 checkpoint 附近的本地 tokenizer |
| tokenizer revision | `77675fc96a7e445e982e2ba90246b816efc74ec6` | checkpoint 记录 |
| encoder `max_position_embeddings` | 8192 | 编码器容量，**不能据此声称 TTS 支持 8192 token** |

源码链：`infer.py:155` 的 `--max-text-len` 默认 None；`inference_runtime.py:706–718` 从 metadata 得到默认长度；当前 `_run_infer` 未传覆盖值。因此本机实际文本长度为 256，caption 为 512，而非看到 CLI 的 fallback 就把二者都当 256。

### 1.2 200 字符来自哪里

`render_queue.py:442` 的 `len(text) > 200` 是 HTTP 计划校验里的硬编码，按 Python Unicode code point 计数。它没有读取 tokenizer、checkpoint 或预计音频时长。**能确定它是独立的工程守卫，不能从当前证据推出“200 是底模算出来的”，也不能补写当年选择这个数的动机。**

`run_infer_synth()` 把 text/caption/cfg/out_wav/ship 交给 `_run_infer`，这里没有显式截断。但模型前处理有截断，见下一节。旧 `/tts`、`/tts_stream` 直接走队列提交，不经过 `/v2/render` 的同一 HTTP `_check_unit`；只改 200 的一行，不能构成全入口输入安全保证。

**本轮新增 CPU 实测**：四份既有日文材料的前 200 字，按运行时规范化后用同一个 tokenizer 计数，均含 BOS：

| 材料 | 字符 | token | 距 256 剩余 | 使用预算 |
|---|---:|---:|---:|---:|
| 大凤 | 200 | 92 | 164 | 35.9% |
| 布雷斯特 | 200 | 100 | 156 | 39.1% |
| 金狮 | 200 | 97 | 159 | 37.9% |
| 阿尔比恩 | 200 | 108 | 148 | 42.2% |

所以这些材料的 200 字只用掉约 **36–42%** token 预算，还余 **148–164 token**。这证明字符防线比较保守，**不证明任意日文 200 字都安全**；数字、符号、罕见字及不同语言会改变比例。不能把 256 token 简化成一个永远正确的日文字数。

### 1.3 300 / 500 / 800 字会怎样

引用上一轮已确认结果，计数含 BOS：

| 材料 | 300 字 | 500 字 | 800 字 | 800 字在默认长度下丢失的 token 数 |
|---|---:|---:|---:|---:|
| 大凤 | 141 | 239 | 389 | 133 |
| 布雷斯特 | 149 | 251 | 406 | 150 |
| 金狮 | 141 | 238 | 385 | 129 |
| 阿尔比恩 | 164 | 276 | 437 | 181 |

分清入口后，答案是：

1. **走现有 `/v2/render`：**这些长度都先被 200 字守卫拒绝，尚未进模型。
2. **直接进当前 `_run_infer`，或绕过该守卫：**`normalize_text()` 后，`tokenizer.batch_encode(..., max_length=256)` 使用 `truncation=True`；BOS 占 1，正文只保留前 255 token。CPU 已确认本机是右侧截断。超长文本不会仅因这个长度自动报错，而会失去尾部条件。
3. **300 字四例：**未触发 token 截断。**500 字：**前三例未触发，阿尔比恩例丢 20 token。**800 字：**四例均截断，损失见表。
4. 这些只证明文本条件是否完整。没有运行 GPU，不能把“未截断”升级成“全念出来、音质正常”；也不能断言超长时恰好漏读多少汉字或多少秒。

还有独立的时长边界：`InferenceRequest.max_seconds` 默认 **30 秒**，本机调用未改；自动 duration 预测及手工 seconds 都会经过范围钳位（`inference_runtime.py:1246`、`:1311–1315`）。因此只放宽 max_text_len，甚至传 `--seconds 60`，都不能自动得到 60 秒完整输出。它和 S 的单元预算、20 秒 render 请求超时是不同的限制。

### 1.4 可复跑的 CPU 证据尺子

下面是复核脚本，放在内存执行即可；不 import 服务启动文件、不建推理模型、不联网。工作目录设为 `D:/AI/Wife/tts/irodori`，用该目录 `.venv/Scripts/python.exe -B` 执行；`material` 指向待检查的 UTF-8 日文材料。

```python
import os, json, struct
from pathlib import Path
os.environ.update(CUDA_VISIBLE_DEVICES='', HF_HUB_OFFLINE='1',
                  TRANSFORMERS_OFFLINE='1', PYTHONDONTWRITEBYTECODE='1')
root = Path.cwd()
ckpt = root / 'checkpoints/model.safetensors'
with ckpt.open('rb') as f:
    n = struct.unpack('<Q', f.read(8))[0]
    header = json.loads(f.read(n))
cfg = json.loads(header['__metadata__']['config_json'])
print({k: cfg.get(k) for k in (
    'max_text_len', 'max_caption_len', 'text_add_bos', 'caption_add_bos')})
from irodori_tts.tokenizer import PretrainedTextTokenizer
from irodori_tts.text_normalization import normalize_text
tokdir = next(p for p in (ckpt.parent/'tokenizer', ckpt.parent.parent/'tokenizer')
              if (p/'tokenizer_config.json').exists())
tok = PretrainedTextTokenizer.from_pretrained(
    str(tokdir), add_bos=cfg['text_add_bos'], local_files_only=True)
material = Path(os.environ['MATERIAL']).read_text(encoding='utf-8-sig').strip()
for chars in (200, 300, 500, 800):
    raw = material[:chars]
    text = normalize_text(raw).strip()
    full = tok.encode(text)
    ids, mask = tok.batch_encode([text], max_length=cfg['max_text_len'])
    kept = ids[0][mask[0]]
    assert kept.tolist() == full[:len(kept)].tolist()
    print(dict(chars=len(raw), normalized_chars=len(text),
               tokens=len(full), kept=len(kept), dropped=len(full)-len(kept)))
```

复跑是复核方法，不是本轮要求再次跑完旧统计；本轮只新增 200 字四例和两个情感缺口的 CPU 探查。

## 2. 两条生产腿：推荐共享规划与受限渲染

### 2.1 现有能力与缺口

现有 `/tts` 与 `/tts_stream` 已接受完整 text，且与 `/v2/render` 共用单 GPU 队列；无需为“整段输入”新起服务。然而 `serve_v2.legacy_plan()` 仍用旧 `_segments → _raw_styles → _sticky → _plan_styles`，不能声称它已经使用 v3 情感状态机。

另一个接线陷阱：`/v2/plan` 的 version=3 分支进入 v3/fusion 规划，不能靠同时传 `mode=strict` 就自动获得整篇 v3 规划；strict 的既有语义在旧版本路径上。需要明确接到共享规划器。

### 2.2 选项比较

| 方案 | 评价 | 主要风险 |
|---|---|---|
| a. 只把 200 改大 | 不采用 | 下游静默截断仍在，30 秒音频上限仍在，旧入口也未统一保护 |
| a+. token 检查后提高单次推理长度 | 可作为后续独立实验 | 超过训练配置长度的完整性、显存、推理时间及发音均未验证；不能直接生产放宽 |
| b. 整篇规划、受限分块、共享条件/状态 | **本轮推荐** | 独立推理之间仍可能有音色/语气接缝；共享状态不能使声学上下文连续 |
| c. 整篇输入，按同一因果规则逐句规划并即时渲染 | b 的最小首版 | 暂不利用未来句；但两种输入模式容易一致，实施面最小 |

先做 c，保留 b 中“全篇证据可见”的可选规划策略。不要把两种策略和模型扩长一起上线，避免出问题无法归因。

### 2.3 最小实施面（本轮不实施）

1. **共享规划核心：**从 `scene_plan` 提供纯函数式的 `plan_sentence(sentence, state, evidence)`；返回 condition、reason 和 next_state。流式会话持有 state；整段请求创建独立 state 并按原文顺序迭代。状态绝不跨请求或音色串用。
2. **整段接线：**既有 `/tts`、`/tts_stream` 使用同一核心；沿用请求/响应形状与队列。用明确的部署开关选择旧规划或新规划，默认和回滚行为写清；不要把改变偷偷塞进“字段兼容”。
3. **两种粒度分开：**自然句决定情感推进，渲染子块只服从 token/时长预算。一个自然句若产生多个 `ja_segments` 或更小块，不可每块重复推进滞回。保留 `parent_id`、局部序号和 `sentence_closed`，每个 parent 最多推进一次；取消重试不能再次加票。
4. **统一输入检查：**在各入口共享的推理前适配器，对实际送模的、规范化后的日文精确计 token，超过 256 必须由规划层按安全句界再分，或明确失败；不许让 tokenizer 静默截断。caption 同样检查 512。先保留 200 守卫，再在评测通过后换成 token/时长约束，别一步放开。
5. **较短句可以连续交付：**生产整段请求可用已有 `/tts_stream` 连续返回；`/tts` 最终一个 WAV 则需要服务端按 PCM 拼成一个容器，不能把多个 RIFF 文件的字节直接相加。
6. **状态提交：**规划状态是可撤销的候选，沿用成功交付路径提交，失败段不伪装成已经听到。当前 S 的 writer 提交点是传输语义，不是 playback ACK，文档必须如此描述。整篇预规划与运行时实际提交状态分开记录。
7. **停顿只加一次：**旧接口已有段间 gap；V2 直接 render 音频没有同一 gap，壳时钟另加 pause。统一适配时避免后端和播放器各补 0.10 秒。

**共享同一条件不等于逐块重判。**稳定长段可共享一个 caption/cfg；有明确转折的段落共享的是状态与证据账本，不是强行全篇一个 caption。

### 2.4 听感、风险和回滚

后端按预算分块是生产执行方式，和听完几份孤立样本后手工挑片拼成“成功长段”不同。但从声学结果看，独立扩散推理仍有接缝风险；一次顺播或一个最终 WAV **不能保证听不出拼接**。本仓库这条路径没有证实可把前段的声学状态无缝带给后段。

因此长段听测必须保留全部边界，记录接缝/停顿位置；不要用剪掉边界、交叉淡化吞字或挑最佳片段掩盖它。若后端分块的接缝不可接受，再单独评估预算内句子合并，或需要声学上下文的更大改造。

回滚按入口开关恢复旧规划、原码本/词典版本与原守卫，模型和 LoRA 不变。升级中的会话固定版本到结束，禁止中途切换状态格式。单次长度探索只在隔离实验中做；上线前要求正文完整、音频无时长钳位迹象、尾字可辨、队列延迟和显存有证据。

## 3. 长段情感：有证据才变化，不默认“起承转合”

### 3.1 可实现的首版规则

**默认保持，局部证据足够才转。**长文本不自动套“起→高潮→余韵”，也不把多句全锁成一种情绪。每个自然句分别记录：原文范围、中文源线索、日文线索、LLM hint、family、level、delivery、置信度、发生切换的理由。

- **明确发声指令**（如有效作用域内的“压低声音/耳语”）可以改变 delivery，不自动把 neutral 改成 intimate。
- **LLM hint** 作为一条有来源的候选证据；没有 hint 或不合法时回退，不增加一条阻塞翻译前的独立模型请求。日语直通没有中文翻译 hint，也必须工作。
- **标点、拟声、重复**是辅助证据；单个问号、省略号或“だめ”不能独立证明亲密/气声。
- **结构**可决定指令作用域和句子边界，不能独立创造高潮。全篇模式可预读到后文，但必须记录哪一条后文使当前条件改变；流式只用已到达信息。
- **声音韵律**是输出验收证据。当前输入只有文本时不存在“已经测到的韵律证据”，不能倒因为果。

沿用现有码本的逐句滞回作为首版基线：promote=0.58、demote=0.42、单次变化不超过 0.34；保持/衰减规则只在自然句完成时推进一次。当前 hold 衰减 0.17、最多 8 次的规则也不能按技术分块重复计算。这些是既有工程参数，**不是校准过的心理概率**。

要换族而证据低置信时保持旧族并记 abstain；首句没有可靠证据回 neutral。fusion_v1 的 P_MIN=0.60、margin=0.20、Q_MIN=0.35 等目前未校准，不能为修一个词条就全局打开融合路线。

### 3.2 两种输入模式的公平边界

整段最小版本先采用同一因果规则，和流式在相同句子/证据序列上应输出相同条件序列。整段未来可用全篇证据形成弧线，但这属于明确标注的另一策略，不要求流式预测未知后文。

作用域必须局部化。桥目前给子段附源线索时，不能把整段开头的一条耳语指令不加区分地传播到所有后句。建议给每条 cue 加源范围/适用 parent_id；“后文恢复正常说话”能终止作用域。翻译 context_before 当前不应被误报为已经完全传入翻译模型并被使用。

## 4. 长段评测：完整听、成对种子、分清比较对象

### 4.1 仓库支持 seed，但生产链尚未透传

**源码确认：**`infer.py:322 --seed` 支持整数；`inference_runtime.py:1174` 无 seed 时用随机值；`rf.py` 用 `torch.Generator(...).manual_seed` 控制采样噪声。当前服务 `_run_infer` 没传 seed，`run_infer_synth` 也没有这项透传。客户端 JSON 多写一个 seed 并不代表已生效。

实施时在现有推理适配器增加可选 seed 的内部透传/实验注入，记录实际使用值；未指定仍保持生产随机行为。不要为它新造长文接口。GPU 确定性还受设备、算子、版本影响：先跑同条件 A/A 验证，不能仅凭 manual_seed 就承诺逐字节一致。

同一长段拆成多块时使用固定 manifest 中的子块 seed（例如预先生成并保存 seed 列表）；两臂切分必须一致。caption 改变可能改变 duration 预测和噪声张量形状，配对 seed 能降低随机混淆，**不保证两臂全部内部随机轨迹相同**。主评测保留自然时长；定时长只作另一个受控实验。

### 4.2 最小材料与比较设计（建议规格，尚未运行）

- **12 段完整材料**：6 类各 2 段，每段约 300–500 日文字符、4–8 自然句。覆盖稳定中性、明确耳语但非亲密、弱声歧义与普通拒绝反例、稳定亲密/气声、明确情绪转折及恢复、长句/数字/控制标记与作用域。材料不用服务端 fit_200 截头。
- 每段 **4 个配对 seed × 2 臂 = 96 份长段输出**。这是工程筛查，不声称已经获得统计显著性；12 个文本是文本泛化的样本数，不能把同文本多 seed 当成 48 个独立文本。
- 另加 **4 个 500/800 字压力材料**，重点核完整性、超限显式行为和状态衰减；不拿它们强行一次推理。160–300 字且 token 合法的子集可另测单次推理与分块差别，30 秒上限仍需检查。
- 先在阿尔比恩做主对照；再从缺口/转折/稳定三类中挑固定材料，对任务所列其他音色作迁移检查。不同 LoRA 的同 caption 效果不默认相同。
- 两臂主要比较旧/新情感条件策略时，**文本、切分、停顿、音色、模型、步数、seed 列表、播放音量固定**。cfg 若随策略改变，把它列为策略的一部分；要单独证明 caption 的收益，就额外固定 cfg。
- “同文本、同条件”适合作 A/A 重复与采样噪声基线，不是情感识别优劣的实验。改变切分又改变条件的两个结果只能说明总体体验差别，不能归因到哪一项；需要时作 2×2 对照。

听测表至少含：匿名编号/顺序、text_id、voice、策略版本、seed 清单、token/分块清单、条件序列、是否完整、漏读/重复、耳语或气声是否准确、普通拒绝是否被误判亲密、转折位置是否合理、情绪稳定性、边界接缝次数及位置、停顿自然度、整体偏好/无差别、备注。隐藏 A/B 标签、交错顺序，加入少量 A/A 隐藏重复，不能只播放每臂最好的一条。

### 4.3 工程验收和听感分开

现有评测脚本若使用 `fit_200` 或只取文本前缀，无法证明长段完整；若将多份 WAV 字节直接相加，无法证明正确顺播。应通过既有生产链路交付完整文本，保存所有子段与 manifest，并顺序解码播放，不手工修音后再评分。

先检查：源范围守恒、所有子段都有明确终态、无静默 tokenizer 截断、无未标注失败、start/end 配对、session.finished。**display.span 全到不等于每句有声音**，failed 段也会显示。

性能记录首个可听帧、翻译/排队/synth/编码、峰值资源与单元失败；真实听感空档应来自实际播放时间轴。客户端若有准确到达时间和音频长度，可计算“理想顺播的供给空档”，但不能冒充扬声器实测空档。所有失败样本保留，失败率不从听测筛选中消失。

## 5. 两个已知缺口：先修条件，不急着训练

### 5.1 neutral 缺耳语能力：缺的是允许组合

**本轮 CPU 复现：**`（息を殺して）気づかれないように……` 在 fresh state 下得到 neutral，delivery=whispered、reliability=0.7，gap=`no_anchor_for_whispered`。本次 caption 是 `自然な声で、丁寧に`，并非任务描述中的 QUIET；具体 neutral 档位受状态影响，但缺耳语映射这个结论不变。

现有码本已有 `柔らかく、優しく囁くように`，但只在 flirty/intimate 梯子内。**最小候选修法：**在新版本条件编译器里，把明确 whispered 的 neutral 映射到一个允许的 neutral+whisper 组合，复用既有耳语 anchor；保持 neutral 的语义族，不靠改成 intimate 绕路。cfg 先作为独立待测组合，不把“已有训练 caption”偷换为“这个新组合已经听测有效”。

新增版本及白名单必须覆盖 planner 与 render 校验，两边同步，旧 v2/v3 不暗改。耳语方向成功、但亲密感被意外带出来，也算失败。

### 5.2 弱日语：默认路线缺族评分，不是整个词典没用

**本轮 CPU 复现：**`……ん、そこ、だめ……` 的 cascade 是 neutral/自然声；`ja_support()` 给 flirty 支持 0.72，但 phonation 为空。默认路径的 delivery 判断已经使用部分日语词典；未接入的是融合路线那套族支持评分。把任务中的“词典只在 fusion”当成完整事实会改错位置。

词典里 `だめ / いや / やめて / そこ` 也可表达普通拒绝、制止、位置。**不能直接把 flirty=0.72 当成可信概率，也不能据此硬指定 breathy。**

最小修法是给 cascade 增加一个作用域明确的弱线索候选阶段：强显式规则优先；短弱声模式须有多项独立支持或前句可信状态才能影响候选；只有歧义词时保持/abstain，并日志记候选未采用。显式耳语走 delivery，普通拒绝反例必须保持正常语义。先用标注集校准该小阶段，不整体开启未经校准的 fusion_v1。

这也意味着：单独给出这一句、没有上下文时，算法不能保证同时“总能判成气声”与“绝不误伤普通拒绝”。若听测期望它必为弱声，材料需带真实上下文或显式发声标注，不能拿歧义文本倒逼误报。

### 5.3 何时需要训练

先试已有 anchor 的条件侧修复，不需要为了多一条码本字符串立即重训。**补一条 caption 字符串不等于教会模型一种声音**；已有文本编码器可能泛化，但声学效果只能听测证实。

尤其当前 breathy anchor 包含“激烈呼吸、甜、近距离”等复合语义，不能当通用 neutral 气声。若已有耳语/气声锚无法在非亲密材料上实现干净发声控制，才收集相应音频与一致 caption，对 LoRA 做有对照的训练。不能先换一个新句子就宣布控制能力补齐。

## 6. 只做一条腿的代价

| 取舍 | 实际损失 |
|---|---|
| 只做流式 | 整篇 text 的既有生产调用仍可能走旧情感逻辑；长篇朗读、整段重放与离线任务条件不一致。外部把全文伪装成碎 token 不是完成整段入口适配 |
| 只做整段 | 对话必须等全篇输入，失去边生成边播；取消和局部失败更难处理。也不能用未来信息规划结果冒充在线可实现的效果 |
| 两腿都做，但各写一套情感规则 | 同文异结果、回归双份，弱声修复一边生效另一边仍坏 |
| 两腿共享规划、按预算渲染 | 满足本轮要求；残留代价是声学分块接缝和未来信息可见性差异，必须在评测中暴露 |

## 7. 实施顺序与本轮结论边界

建议顺序：① 固化完整性/token/状态推进的 CPU 测试；② 统一两个入口的规划核心及推理前守卫；③ 新版本 neutral-whisper 组合与小范围弱线索候选；④ 固定种子透传及长段盲测；⑤ 证据不足时保留原长度，不扩大底模上下文。每步保留旧版本回滚，未完成听测不默认开启新组合。

本轮 CPU/只读证据：checkpoint header 和加载路径；新增四份 200 字 tokenizer 统计；两个已知缺口的纯规划输出；相关源码逐链检查。历史 300/500/800 统计与 9/9 边界检查为用户确认的前轮证据。

**尚未验证：**放宽 token 长度后的 GPU 稳定性/显存/完整发音；新 anchor 组合的跨音色效果；双入口共享规划的实现；固定 seed 的端到端实际透传；分块接缝、长段主观听感及真实播放性能。本文不给这些项目虚构验收结论。

审计范围为本轮开工记录的 76 个输入文件（源码、配置、tokenizer、LoRA metadata、任务书及前两版方案）；交付前已重算 MD5，**76 个中变化 0 个**。本轮仅新增本文；完整 checkpoint 本轮只读 JSON 头，没有为审核额外重算 3 GB 权重散列。
